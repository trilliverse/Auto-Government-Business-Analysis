# Stage 1 业务人员使用说明

## 需要准备什么

必需：

1. 单位名称；
2. 处室名称；
3. 含职责原文的文件；
4. 说明职责来源是否为正式现行版本；
5. 说明本次全部纳入，还是排除/只纳入某些职责；
6. 说明特殊口径，没有则回答“无”。

不需要上传《广东省交通运输厅职能清梳理工作指引》。其方法已经内置到 Agent。

## 在 Harness 中如何说

选择“政务流程梳理”后，可直接输入：

> 新建职责梳理案件。单位是……，处室是……。职责材料在……。请先提取职责并让我确认，不要直接生成最终 Excel。

Agent 应依次展示：

1. 单位、处室和职责条款；
2. 职责来源及是否核验；
3. 纳入/排除范围；
4. 特殊规则；
5. Gate 0 审核稿。

只有业务人员明确确认后，Agent 才进入职责拆解。

## 如何审核拆解结果

重点检查：

- 是否漏项或过度拆分；
- “承担、参与、指导”等责任边界是否保留；
- 并列对象补齐后是否改变原意；
- 督导、组织、负责、参与分类是否符合本单位实际；
- 领导交办等兜底事项是否纳入。

可以用自然语言提出修改，例如：

> I005 的分类改为待确认；R008 本次排除；I010 不要补充原文没有的主体。

Agent 应生成新草稿或审核变更，不得覆盖已经批准的版本。

## 批准后得到什么

- 不可变 Stage 1 JSON；
- 四列 Excel：处室名称、职责、事项、职能类型；
- 审核决定和版本哈希；
- 后续 Stage 2 使用的稳定事项 ID。

## 后续阶段如何查看状态

业务人员通常通过对话继续；管理员可使用 `case_status.py` 查看当前阶段，使用 `audit_case.py` 生成完整版本链和未决问题报告。任何下游成果都必须绑定上游批准哈希，上游变化后需要重新生成和审核。

## 何时需要补充正式文件

出现以下情况时，先补材料，不要直接批准：

- 工作簿职责与正式三定文件可能不同；
- 存在职责调整文件；
- 两份来源互相冲突；
- 无法确认职责是否仍然有效；
- 需要把结果作为正式职责依据对外发布。
