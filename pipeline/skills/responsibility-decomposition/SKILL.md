# 职责原子化拆解与分类

## 使用前提

仅在案件 `case.json` 处于 `stage-1`，且 Gate 0 批准文件绑定当前 `input_version` 和职责来源 SHA-256 时使用。否则停止并提示先完成输入审核。

读取 `inputs/responsibilities.json`，不得使用后续 Excel 中经过合并或改写的事项反向替代职责原文。

工作指引的方法原则已内置，普通案件不要求业务人员上传《广东省交通运输厅职能清梳理工作指引》。只有在需要核验方法版本或变更口径时才把原 PDF 作为治理参考，不作为业务事实证据。内置依据摘要见 `pipeline/docs/stage1-method-basis.md`。

## 输出目标

为每条职责生成一个或多个原子事项草稿。每项至少包含：

- `item_id`：稳定且唯一；
- `source_responsibility_id`；
- `source_sequence` 和 `item_sequence`；
- `item_text`：含完整责任状态、动作、业务对象和必要范围；
- `action`；
- `object`；
- `category`：督导、组织、负责、参与、待确认之一；
- `derivation_note`：仅说明共享成分如何补齐，不写入交付事项；
- `issues`；
- `status: draft`。

## 拆解规则

1. 严格按职责顺序处理，不跨职责合并，不擅自删除兜底职责；排除仅能由人工审核决定。
2. 识别完整动作前缀，例如“贯彻执行”“参与拟订”“承担指导”。保留“承担、参与、协助”等责任边界。
3. 不同动作强制拆分；同一动作下不同业务对象或管理环节通常拆分。
4. 拆分后补齐原句中共享的动作、对象和“事务性工作”等限定，使事项可独立理解。
5. 不机械拆分固定政务名词，例如“方针、政策和法律法规”；不拆完整闭环动作，例如“调查处理”。
6. 补齐共享成分时保持原句语法和措辞：原文为“项目备案、计划、绩效考核等事务性工作”时，拆分后写“项目备案事务性工作”“项目计划事务性工作”“项目绩效考核等事务性工作”，不得统一增添“的”，不得丢失末项承接的“等”。
7. 共享修饰语按原句最近支配关系处理。例如“国省干线公路养护造价、养护市场管理及信用体系建设”中，“国省干线公路”覆盖三项，“养护”只保留在原文明确带有的“养护造价、养护市场管理”，不得自行补为“养护信用体系建设”。
8. C 类事项文本是结构化拆解表达，不要求机械逐字摘录，但不得引入原文不存在的权力、主体、材料或结果。
9. 对有歧义的并列修饰范围，不得硬猜：保留较稳妥表达并写入 `issues`，分类用“待确认”。

## 分类规则

工作指引提供四类职能的语义框架；以下关键词、复合动作覆盖和冲突处理属于本项目执行口径，不应全部表述为工作指引原文。先判断复合动作，再判断单一核心动作：

- 督导：指导、检查、监督、督促、考核、备案、督导、督察；
- 组织：组织、统筹、牵头、召集、推进；
- 负责：承担、承办、负责、实施、执行、拟订、编制、起草、制定、管理、建设、审批、贯彻落实；
- 参与：参与、协助、辅助、配合、提出意见或建议。

复合动作覆盖：

- 组织实施、组织开展 → 负责；
- 组织协调、统筹协调 → 组织；
- 监督实施、监督执行 → 督导；
- 负责指导、承担指导、承担督导或监督 → 督导；
- 参与拟订、参与编制 → 参与；
- 提出意见或建议 → 参与；提出目标或规划 → 负责。

分类针对原子事项的核心业务动作，而不是只取句首第一个词。“承担项目备案”和“承担项目绩效考核”虽然以“承担”开头，核心动作分别是“备案”“绩效考核”，均归督导；“承担项目计划”核心动作是计划，按负责。`action` 字段可保留责任前缀，但分类必须扫描完整动作短语。

当词表冲突且复合规则仍不能消歧时，分类为“待确认”，在 `issues` 写明冲突。

## 质量检查

生成审核稿前必须检查：

1. 所有来源职责至少有一条事项，除非明确标记为待人工排除；
2. 每项都能回指唯一来源职责；
3. 顺序连续、ID 唯一；
4. `item_text` 不含末尾分类标签；
5. 分类只使用受控枚举；
6. 不将事务性、参与或指导职责提升为最终审批或主办权；
7. 记录模型/Skill 版本和当前输入哈希。

## 人工审核

输出只写入 `stage-1/drafts/`。同时生成 Markdown 审核稿，逐项展示来源职责、草稿事项、分类、拆解说明和问题。

人工可以修改、拆分、合并、改类、排除或退回。Skill 不得自行创建批准决定，不得写入 `stage-1/approved/`，不得自动进入 Stage 2。
