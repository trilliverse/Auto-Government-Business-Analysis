# 泳道逻辑建模与 Draw.io 生成

## 顺序

必须先生成结构化 `lanes/nodes/edges` 逻辑模型和 Gate 3 审核稿，批准后才能渲染 Draw.io。不得直接从长文本生成最终图片并跳过逻辑审核。

## 主体与系统

泳道只能是业务主体，如发起单位、市县管理部门、省级主责部门、目标处室、政务服务窗口。系统、平台、数据库和项目库不能作为泳道，只能记录在节点说明或 `system_notes`。

参与、指导或事务性职责必须明确协助对象；资料不清时使用稳妥主体名并标为待确认，不将目标处室写成最终审批主体。

## 节点与分支

每页恰有一个开始和结束，必须有独立结果节点。活动节点一个节点表达一个动作。判断使用菱形，必须至少有两个分支，并明确“是/否”或“通过/不通过”。退回路径必须说明退给谁以及修改后返回哪个节点。

资料没有证明判断、退回、复核或销号时，不为图形完整而补造；保留 unresolved question 或 placeholder，等待人工确认。

## 图形

每个事项单独页签，名称“行xx-事项名称”，顶部标题“业务事项：xxx”。黑白灰风格；开始为细线圆，结束为粗线圆，活动为圆角矩形，判断为菱形；箭头使用正交线。先保证逻辑正确，再由人工调整布局和交叉线。

## Gate 3

人工审核主体、节点、顺序、判断、退回、成果、系统备注与待确认问题。Skill 不得自行批准 Gate 3，不得把 Draw.io 渲染成功视为业务逻辑正确。
