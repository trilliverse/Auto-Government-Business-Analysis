# Pipeline 架构与阶段路线

## 1. 目标

把现有依赖手工上传附件和复制 Prompt 的工作方式，转为可追溯、可暂停、可人工修改并继续运行的半自动流程。流程不得因为模型输出看似完整而越过人工审核。

## 2. 总体状态机

```text
Gate 0 输入确认
  -> Stage 1 职责拆解草稿
  -> Gate 1 职责事项审核与版本冻结
  -> Stage 2 证据检索、数字化判断和流程草稿
  -> Gate 2 证据与流程审核、版本冻结
  -> Stage 3 泳道图逻辑模型
  -> Gate 3 流程逻辑审核
  -> Draw.io 渲染及人工排版
  -> Gate 4 发布与交付
```

每个 Gate 的批准对象必须是一个不可混淆的具体版本。上游批准版本变更时，下游标记为 `stale`，不得静默沿用。

## 3. 数据层、审核层和呈现层

### 3.1 数据层

JSON 是 Pipeline 内部事实源，保留稳定 ID、输入哈希、原文、定位、版本、状态和审核记录。Excel 不作为跨阶段的唯一事实源。

### 3.2 审核层

每阶段输出 Markdown 审核稿以及机器可读的审核决定。后续可按实际需要增加 Web 审核界面，但 MVP 不依赖 UI。

### 3.3 呈现层

Excel、Draw.io、图片和报告均由已批准结构化数据导出。呈现格式可以变化，不反向覆盖已经批准的数据。

## 4. 各阶段核心对象

### Stage 0

- `CaseManifest`：案件、组织、当前状态、输入引用；
- `SourceDocument`：路径、文件哈希、工作表和单元格定位；
- `ResponsibilitySource`：职责原文和条款切分。

### Stage 1

- `ResponsibilityItem`：稳定 ID、来源职责 ID、完整事项、动作、对象、范围、职能类型、问题与状态；
- `ReviewDecision`：对具体版本的批准、退回或修改请求；
- 原文不得被模型输出覆盖。

### Stage 2

- `EvidenceRef`：文档哈希、页码/章节、短引文、支持的结论字段；
- `DigitalSupportAssessment`：有、无、待确认、不纳入；
- `WorkflowDraft`：主体、材料、步骤、结果、待确认问题，区分直接依据、业务整理和人工补充。

### Stage 3

- `SwimlaneModel`：泳道、节点、边、判断分支、系统支撑注释和未决问题；
- 先批准逻辑模型，再渲染 Draw.io；系统不能作为业务泳道。

## 5. Skill、Tool、Workflow 和 Preset 边界

### Skill

保存领域方法、分类规则、提示模板、质检清单和暂停条件。Skill 不保存案件状态，也无权批准阶段。

### Tool

执行确定性、可审计操作：Excel/PDF 读取、哈希、Schema 校验、版本保存、审核决定校验、Excel/Draw.io 导出。重复执行应尽可能幂等。

### Workflow / 子智能体

只用于有边界的批处理，例如 Stage 2 按事项并行检索证据，再统一汇总。不得用一个长时间运行的 workflow 等待人工审核。

### Agent Preset

提供面向业务梳理人员的角色提示、Skills 和必要工具。跨会话状态仍落在工作区案件目录；共享注册表、审批、沙箱和模型路由留在 Host plane。第一阶段工具与规范稳定后，再从 `standard` 复制专用用户 Preset，避免过早固化。

## 6. 人工审核闸门

### Gate 0：输入确认

确认材料、单位、处室、职责原文、切分边界和适用口径。未批准不能启动 Stage 1。

### Gate 1：职责事项确认

逐条允许编辑、拆分、合并、改类、排除或退回。必须核对事项来源；重复项可标记但不能擅自删除。批准后冻结版本。

### Gate 2：数字化及流程依据确认

核对业务对象范围、系统匹配、主流程、处室责任、证据定位和待确认问题。“系统具备能力”不得直接写成“处室实际使用”。

### Gate 3：泳道逻辑确认

先核对主体、节点、判断、退回路径和最终成果，再生成图形。信息不足时保留待确认，不补造闭环。

### Gate 4：发布

执行跨阶段引用一致性、数量、版本、格式和导出物检查，冻结交付版本。

## 7. 第一阶段 MVP 验收标准

1. 对示例工作簿稳定提取 8 条职责；
2. 每条职责保留完整原文、稳定 ID 和 `工作簿#工作表!单元格` 定位；
3. 输入文件保存 SHA-256，审核决定绑定输入版本与哈希；
4. 校验器拒绝缺失字段、重复 ID、非连续序号、错误哈希和失效批准；
5. intake 重复运行相同输入得到相同职责内容和哈希，不覆盖人工决定；
6. 未获 Gate 0 批准时明确停在 `awaiting-input-review`；
7. Stage 1 后续草稿必须使用受控分类枚举，并允许 `待确认`，不能硬猜。

## 8. 后续开发顺序

1. 完成本轮 Stage 0 工具与测试；
2. 用示例结果建立 Stage 1 黄金集；
3. 实现职责拆解 Skill 的模型执行与结构化校验；
4. 生成人工可编辑审核稿和差异记录；
5. 实现批准版本冻结和 Excel 导出；
6. 再开发 Stage 2 文档索引、证据检索与按事项并行分析；
7. 最后开发 SwimlaneModel 和 Draw.io 渲染。
