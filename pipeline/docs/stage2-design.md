# Stage 2｜数字化支撑、证据与流程底稿设计

## 目标

Stage 2 读取 Gate 1 冻结的事项版本，不直接读取可变草稿。逐事项形成数字化判断、流程叙述、系统关联、证据引用和待确认问题。

## 两步法

### 2A：文档编目与证据候选

1. 对输入文件计算 SHA-256；
2. 记录媒体类型、业务范围和版本；
3. 提取带页码或章节锚点的文本片段；
4. 按事项检索候选证据；
5. 人工可删除错配候选或补充资料。

### 2B：逐事项分析

可按事项并行调用子智能体，但每个结果必须使用统一 Schema。汇总器仅执行来源检查、枚举校验、跨事项一致性检查和审核稿生成，不得代替人工放行。

## 证据边界

每条结论区分：

- `evidence_refs`：文档直接证据，必须含文档 ID、页/章/节定位和短引文；
- `inference_notes`：由多处证据整理出的业务逻辑；
- `human_additions`：业务人员补充的系统、主体或流程；
- `unresolved_questions`：仍未确认的主体、材料、权限、退回路径或成果。

数据库字段只能证明数据结构，不能单独证明角色、审批程序或状态转换。背景关键词只能标记为 `context-only`，不能据此判定数字化主流程。

## 数字化状态

- 有：主要业务过程已获得较强支撑；
- 无：有材料或人工意见支持本轮“无”的判断；
- 待确认：仅有零散线索或适用对象不清；
- 不纳入本次梳理范畴：有明确范围依据。

资料缺失不得自动判“无”。“系统具备能力”不得自动表述为“目标处室实际使用”。

## Gate 2

人工逐项核对：

1. 事项与业务对象没有错配；
2. 数字化状态证据充分；
3. 主责、参与和事务性角色没有被扩大；
4. 系统名称、编号和来源明确；
5. 流程中的主体、材料、动作、反馈和成果可追溯；
6. 待确认问题没有被模型虚构补齐。

批准绑定 Stage 1 批准产物哈希和 Stage 2 草稿哈希。上游 Stage 1 版本变化后，Stage 2 自动失效。
